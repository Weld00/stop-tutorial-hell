## Recognize the loop

You may recognize this pattern; it is not an explanation of everyone's learning difficulties:

```text
More options -> another course -> follow-along progress
      ^                                 |
      |                      a real task gets blocked
      |                                 |
      +---------- start over <----------+

Try instead:
one bounded task -> small attempt -> inspect the result -> review
```

A lesson can be useful. The question is whether it helps you attempt or understand a specific task, rather than only adding another open-ended commitment.

## The four-step protocol

### 1. Audit the calendar and the conditions

- [ ] Name a situation you want to change.
- [ ] Separate checked facts from guesses.
- [ ] Count sessions you can actually protect, including setup and review time.
- [ ] Check budget, permitted inputs, tool access, and available feedback.
- [ ] Ask whether the next step is learning, acting with existing knowledge, or clarifying a missing fact.

There is no universal five-hour minimum or ideal weekly range here. If the task does not fit your sessions, narrow it or gather a missing fact. Do not convert an unavailable environment into a verdict about the whole skill.

### 2. Choose one focus and make deferral explicit

Compare the purpose, access, time, feedback, unknowns, and actual cost of waiting for each option. Include an act-first or clarify-first option when appropriate.

Copy this note or use [DEFERRAL.md](DEFERRAL.md):

```markdown
## My revisitable deferral note
- Current focus or next clarification:
- Why it fits the facts available now:
- Review date:
- Deferred option:
- Reason it can wait:
- Evidence or changed condition that would reopen it:
- Supporting tools or necessary learning I still need:
```

Deferral means "not my active project now," not "worthless" or "forbidden for 30 days." Keep legitimate side interests, required prerequisites, and changed responsibilities in view.

### 3. Review inspectable evidence around Day 7

Choose one small result you can attempt safely and explain. A first-week review is a prompt, not a deadline after which tutorials are banned.

| Focus | Following instructions alone leaves this unknown | A bounded artifact to inspect | A check that could reveal a problem |
| --- | --- | --- | --- |
| Python | Can I handle an input the instructor did not supply? | Convert a synthetic CSV to JSON with a short script. | Test a missing header, an empty field, and a quoted comma. |
| SQL | Does the query answer this question correctly? | Save one query and its expected result on a permitted sample. | Check duplicates, NULL values, and known totals. |
| Frontend | Can someone use the main action and understand failure? | Build one local page with an input, output, and error state. | Try keyboard input, a narrow viewport, and invalid input. |
| AI-assisted work | Can I review variable or incorrect output? | Keep a task brief, prompt, test inputs, and a review checklist. | Compare expected criteria with outputs, including one difficult case. |

[RECIPES.md](RECIPES.md) expands these examples. Public deployment, a complex tech stack, or an arbitrary number of failures is not required.

- [ ] Record what you actually attempted and where the evidence is.
- [ ] Include setup, checking, and restart time.
- [ ] Separate an incorrect result from missing access or prerequisites.
- [ ] Record what the test cannot establish.

Documentation, tutorials, and AI assistance are allowed. Keep track of help used, explain the result, and make one meaningful change without replaying the whole solution. Do not publish private data as proof.

### 4. Write review conditions before expanding

Use conditions as questions to revisit, not a mechanical career score:

| Next decision | Evidence to look for |
| --- | --- |
| Continue | The task serves the goal, the checks are meaningful, and the next attempt fits current conditions. |
| Narrow | The task is useful but its scope or restart cost exceeds the sessions available. |
| Clarify or retry | Missing access, setup, or a prerequisite prevented a meaningful attempt. |
| Defer | Another current need matters more, or the required condition is not available yet. |
| Stop this test | The need disappeared, the method does not meet it after a meaningful check, or a simpler existing approach serves it. |

Enjoying debugging does not prove career fit. Spending a fixed percentage of time on setup does not automatically require a pivot. Not attempting a task is missing evidence, not proof that the direction is wrong.

## Weeks 2–4, if the first review supports continuing

- **Week 2:** repeat or extend the useful part.
- **Week 3:** test changed inputs, errors, and limits.
- **Week 4:** package the result, explain it, and review what deserves attention next.

Adjust the stages after interruptions or changed circumstances. A month does not certify mastery, and you do not have to rotate to a new skill on Day 30.
